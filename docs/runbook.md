# 运行手册

给 GPT、Codex、Cursor 和人工一个固定操作顺序，使新任务可重复执行：启动 → 分流 → 执行 → 验证 → 审批 → 提交 → 归档。

**实际执行任务时，以本文作为操作顺序入口。**

## 运行手册目标

1. 任何人接手任务时知道先做什么、后做什么
2. 风险、验证、审批不靠口头约定
3. 完成后有统一输出与归档，结果可回流

## 标准操作顺序

```text
1. 新建或读取任务单
2. 检查风险等级
3. 按分流规则确定执行者
4. 执行前确认影响范围和不做什么
5. 执行变更
6. 按验证层要求检查；有 CI 时先本地复现
7. 高风险任务进入人工审批，不得擅自执行
8. 输出变更总结、影响范围、验证结果、风险与待确认
9. 更新任务状态和 backlog
10. 需要时创建 Git commit
11. 记录到 pilot-log 或对应归档文件
```

## 新任务启动流程

1. 用 [`docs/task-template.md`](task-template.md) 新建任务单，或读取 `tasks/T00x-*.md`
2. 登记到 [`tasks/backlog.md`](../tasks/backlog.md)；状态默认 `待办`，高风险为 `待确认`
3. 必须写清：目标、影响范围、不做什么、验收标准、风险等级、推荐执行者、测试命令

## 任务分流流程

按 [`docs/ai-task-routing.md`](ai-task-routing.md)：

1. 需求不清 → GPT 澄清
2. 高风险 → 先人工审批（见下），再执行
3. 整仓明确改动 → Codex
4. 局部调试 / UI / 结对 → Cursor
5. 迁移、支付、权限、安全、生产、真实用户数据 → 人工主导

## 执行前检查

- [ ] 影响范围与「不做什么」已确认
- [ ] 风险等级已标明；不确定则上调，不擅自降级
- [ ] 高风险：已按 [`docs/risk-approval.md`](risk-approval.md) 取得审批，否则**停止**
- [ ] 测试命令 / 验证类型已写明（见 [`docs/verification.md`](verification.md)）

## 执行中规则

- 只改任务所需文件，不做无关重构
- 遵循现有代码风格与目录约定
- 不引入未说明的新依赖
- 发现范围蔓延或需求模糊 → **停下并询问**
- 触及禁止动作（未审批的改库、迁库、生产、真实用户数据等）→ **立即停止**

## 验证要求

按 [`docs/verification.md`](verification.md) 与任务单「测试命令」执行最低验证；不得把「未跑」写成「通过」。对照 [`docs/definition-of-done.md`](definition-of-done.md)、[`docs/ci.md`](ci.md) 与 [`PR_CHECKLIST.md`](../PR_CHECKLIST.md)。

## 高风险审批要求

高风险任务必须先查看并遵守 [`docs/risk-approval.md`](risk-approval.md)：

- 未审批：不得改相关代码、生成迁移、连库、发生产、处理真实用户数据
- 审批记录须含：审批人、时间、范围、允许动作、回滚方案
- 示例门禁：`tasks/T004-high-risk-gate-sample.md`（未审批前不执行）

## 完成后输出格式

```text
## 变更总结
- ...

## 影响范围
- ...

## 验证结果
- 执行了哪些验证：...
- 验证结果：通过 / 失败 / 未跑（原因）
- 未覆盖的风险：...
- 是否需要人工确认：是 / 否

## 风险与待确认
- ...
```

## Git 提交流程

1. `git status` / `git diff` 确认仅含任务范围内文件
2. 确认无密钥、无意外业务或 CI 改动（除非任务明确要求）
3. 仅在用户要求或任务明确要求时创建 commit；message 简洁说明「为什么」
4. 提交后确认工作区是否干净，并回报 hash

## 远程推送与失败降级

默认仍须用户明确同意后再 push。同意后：

1. 优先 CLI：`git push` 或 `scripts/push-with-fallback.ps1`
2. **失败不死等**：记本地 tip，写入 `.pending-desktop-push.json`，标「待人工 Desktop 推送」
3. 向用户回报固定句式；网络恢复后再发 `同意推送三方闭环`
4. 详细策略见 [`docs/push-fallback.md`](push-fallback.md)

## 任务归档流程

1. 任务单与 `backlog.md` 状态改为 `已完成`（或 `已取消` 并写原因）
2. 里程碑 / 试跑结果写入 [`docs/pilot-log.md`](pilot-log.md) 或约定归档文件
3. 可复用的经验回流到规则文档（`AGENTS.md`、Cursor rules、本手册等）

## 不确定时

出现以下任一情况，**停下并询问**，不猜测继续：

- 需求、边界或验收不清
- 风险等级无法判断
- 需要新依赖、改生产配置或触达真实数据
- 审批记录不完整
- 验证失败且修复方案会扩大范围
