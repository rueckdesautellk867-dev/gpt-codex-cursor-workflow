# 验证层设计

统一后续任务的验证方式：何时算「测试通过」，何时必须人工复核。  
当前标准已接入最小真实 CI，详见 [`docs/ci.md`](ci.md)。

## 验证层目标

1. 每个任务单可写明「测什么、怎么测、谁复核」
2. 按风险等级设定最低验证门槛，避免低风险过测、高风险漏测
3. AI 交付必须可核对：跑了什么、结果如何、还剩什么风险

相关：[`docs/definition-of-done.md`](definition-of-done.md) · [`PR_CHECKLIST.md`](../PR_CHECKLIST.md) · [`tasks/README.md`](../tasks/README.md)

## 验证类型

| 类型 | 用途 | 典型场景 |
|------|------|----------|
| Markdown / 文档检查 | 链接、标题层级、格式 | 纯文档、规则、任务单 |
| lint | 风格与静态问题 | 有源码的改动 |
| 类型检查 | 类型安全 | TypeScript / 带类型的项目 |
| 单元测试 | 模块行为 | 逻辑 / 工具函数变更 |
| e2e 测试 | 关键用户路径 | UI / 主流程变更 |
| 构建检查 | 可编译可打包 | 影响构建配置或入口 |
| 安全扫描 | 依赖与已知漏洞 | 依赖升级、对外接口 |
| 人工复核 | 判断与授权 | 高风险、模糊验收、生产相关 |

任务单「测试命令」栏应写出将使用的类型；没有自动化时写明替代检查（如文档链接检查）。

## 风险等级与最低验证要求

### 低风险

- 最低：Markdown / 文档检查（格式、链接）；或任务单约定的轻量检查
- 必要时：**无需**自动化测试（须在任务单与交付说明中写明）
- 人工复核：通常不需要，除非触及对外发布文案等约定项

### 中风险

- 最低：至少包含 **lint**、**类型检查**（若项目适用）、**相关单元测试**
- 影响构建时加上构建检查；影响主路径时考虑 e2e
- 人工复核：建议对 diff 与测试结果做一次抽查

### 高风险

- **必须先人工确认**，再进入实现
- **必须有回滚方案**（回退提交 / 关开关 / 还原迁移等）
- **必须写清数据与权限影响**（库表、用户数据、鉴权、支付等）
- 自动化测试按中风险执行，且不得替代人工确认
- 未确认前状态保持 `待确认`，不得改为 `进行中`

## 「测试通过」判定

同时满足才可写「测试通过」：

1. 任务单写明的验证类型均已执行（或已声明不适用及原因）
2. 适用的自动化命令退出码为成功；文档类则链接/格式检查通过
3. 未把「未跑」写成「通过」；未跑须单独列出
4. 高风险：人工确认记录已存在，且回滚与数据/权限影响已写明

## AI 输出必须包含

完成任务时，验证相关说明至少包含：

```text
## 验证结果
- 执行了哪些验证：...
- 验证结果：通过 / 失败 / 未跑（原因）
- 未覆盖的风险：...
- 是否需要人工确认：是 / 否（原因）
```

可并入项目统一的变更总结结构（见 `AGENTS.md`）。

## 与后续 CI 的关系

- 本文是验证**标准**；真实流水线见 [`docs/ci.md`](ci.md)
- CI 已覆盖文档型项目的基础检查：关键文件、Markdown 链接、任务索引、高风险样例状态
- CI 仍只是自动化载体；风险门槛、AI 输出字段和高风险人工确认仍以本文为准
